# 问题画廊 · Question Gallery — 设计

2026-11-23 · 状态：**待批准**

## 意图与原因

705 个 claude.ai 历史对话里，你问过上千个问题。这些问题分散在对话里、被多轮追问切开、
结尾还挂着 `give me markdown artifact` 这类协议后缀，没法一眼看清"我到底关心什么"。

这个画廊把这些提问抽出来、归一成自洽的标准问题、按主题分模块呈现，供你回顾和深入分析。
数据只读，全部本地，不联网。

## 目标

- 每条提问包含：**标准问题**（自洽、可直接复制）、**原始提问**（逐字）、来源对话、日期、主题
- 按**主题模块**浏览；模块内可搜索、按问题类型筛选
- 每个问题可一键复制：标准问题 / 原始提问
- 能从问题跳回来源对话并定位到那条消息
- 重复的问题合并成一条，但**每一处原文都保留可查**

## 非目标

- 不总结、不评价 Claude 的回答。这是问题索引，不是答案库
- 不做 LLM 生成的"洞察/建议"面板
- 不引入依赖或框架，不加服务端接口（静态 JSON 足够）

## 反目标（技术上跑通也算失败）

- 分类看着整齐但归属可疑 → 宁可少分类、保留"未分类"兜底
- 标准问题过度改写、丢掉原始意图 → 原文永远可见，不折叠删减
- 重复问题刷屏（同一需求在数据里最多重复 224 次）
- 把提取结果当成"已完成"却不做去重，导致数量虚高

## 约束

| | |
|---|---|
| 数据 | `web/data/chats/*.json`，705 个对话；424 个带英文 `summary`，281 个没有 |
| 人类消息 | 1,457 条 → 见下面的数字口径 → **1,017 条实质文本 + 230 条附件类** |
| 协议噪声 | 284 条带 `markdown artifact` 类后缀；另有"你现在是著名作家…"式角色设定 |
| 重复 | 实质消息里 107 次重复出现（按次数）；按种类是 59 种文本重复（40 种同对话重试、19 种跨对话） |
| 现有栈 | 零依赖 vanilla JS；路由是 `#/` 上的简单分派；样式变量集中在 `web/styles.css` |
| 提取方式 | 子代理并行；每个子代理只读，只写自己那一份 JSON |

分类**不预设**，由数据驱动收敛；但"问题类型"用固定枚举，保证跨片一致。

### 数字口径（`--check` 与头部文案的唯一依据）

```
1,457  人类消息
- 224  空文本（无文字）
- 151  continue 类
-  65  1–19 字且非 continue（"fix the err"、"构建 front design"）
─────
 1,017  实质文本消息
   910  其中文本唯一
   107  重复出现次数（按次数，不是按种类）

待纳入范围（已决定算作问题）：
   214  只有附件、没有文字
    16  短文字带附件
─────
   230  附件类消息

工具的实际取用规则（`isCandidate`）：
   排除 文本为空且无附件（仅 10 条）
   排除 continue 类（151 条）
   ─────
   提取输入 1,296 条消息，切成 36 片（每片 20 个对话，每片 ≤32KB UTF-8）
```

`1017 − 910 = 107` 是**重复出现次数**；"59 种文本重复"是**按种类**计的，两者不冲突，
文档与 UI 必须分别标注口径，不得混用。

## 方案

**A — 只按消息提取。** 每条实质人类消息 = 一个问题。
取舍：不丢东西、标签直接来自原文；但同一需求被拆成"先搜索 / 再写成文章 / 继续"好几条，
列表会被切碎。

**B — 只按对话归一。** 一个对话产出 1 条标准问题，用 424 份现成 summary 当输入。
取舍：最省、最接近"我当时在解决什么"；但 summary 是 Claude 的措辞而不是你的，
多需求对话会被压成一条，且 281 个对话没有 summary，仍要读原文。

**C — 按消息提取 + 按对话归一（选定）。** 问题主体按消息提取（A 的明细），
同时给每条标注 `subject`，据此生成按需求的归并视图（B 的概览）。
取舍：两个粒度都在，最贴合"深入分析"；代价是条目多、去重和聚类要认真做。

## 已定决策（你的选择）

| 议题 | 决定 | 影响 |
|---|---|---|
| 模块归属 | **主模块唯一 + 0–2 个副标签** | 模块计数不重叠；副标签只作筛选，不生成模块卡片 |
| 跨对话重复 | **合并成一条**，卡上显示"出现在 N 个对话" | 记录存 `sources[]`，逐字原文全部保留、可展开 |
| 短消息（1–19 字，65 条） | **算** | 从上下文补全成完整问题 |
| 附件消息（214 + 16 条） | **算** | 标准问题点名附件；单独标记，可一键筛掉 |

预期总量约 **1,250 条**，去重合并后为最终条数（`--check` 报告实际值）。

## 设计（方案 C）

### 数据流

```
web/data/chats/*.json  (705)
  │  tools/questions.mjs --digest      切片 + 剥离噪声字段（含附件名与前 ~200 字）
  ▼
web/data/qdigest/part-NN.json          20 个对话/片，只含 convId/name/date/summary/human msgs
                                       text/summary/snippet 按**字节**截断，保证一片能一次读完
  │  子代理并行（只读，各写一片）
  ▼
qwork/part-NN.json                     提取结果（保留为交付物；**不能放 web/data**）
qwork/modules.json                     标签 -> 模块的对应表（聚类产物，同样保留）
  │  tools/questions.mjs --merge       规范化 + 去重合并 + 按表分配模块
  ▼
web/data/questions.json                { modules[], questions[] }（可由 qwork 重建）
  │  tools/questions.mjs --check       schema + 覆盖 + 数量口径校验
  ▼
#/questions  →  #/questions/<module-id>
```

### 数据 schema

```json
{
  "id": "q-0001",
  "std": "为职位描述抽取专业信息：改进 MajorMatcher 类，输出匹配规则、类别与评分",
  "kinds": ["技术实现"],
  "subject": "职位描述专业信息抽取",
  "module": "text-matching",
  "subtags": ["Python", "文本匹配"],
  "tags": ["Python", "文本匹配", "数据抽取"],
  "hasAttachment": false,
  "sources": [
    {
      "convId": "039fffd2-…",
      "convName": "Analyzing Code for Extracting Professional Information…",
      "date": "2026-01-08",
      "msgIds": ["3001e54a-…"],
      "orig": "改进并重写整个 MajorMatcher 类…"
    }
  ]
}
```

```json
{
  "modules": [
    { "id": "text-matching", "name": "文本匹配与抽取", "desc": "从非结构化文本里取出结构化信息", "count": 42 }
  ]
}
```

- `module` 是**唯一主模块**，指向 `modules[].id`，`modules[].count` 因此互不重叠
- `subtags` 0–2 个，纯筛选用，不参与模块计数
- `tags` 是完整标签表，只作为聚类输入，不直接展示
- `sources[]` 至少 1 项；合并来的重复全部在这里，逐字原文一条不丢
- `id` 用固定前缀 slug，路由用 `#/questions/<modules[].id>`

### 标准问题的改写规则（子代理指令要点）

1. 保留原始意图与约束，不添加原文没有的要求
2. 剥离：`give me markdown artifact` / `markdown artifacts one by one` 等协议后缀；
   "你现在是著名作家/游戏策划大师…"式角色设定；单独的 `continue`
3. 自洽：脱离对话也能看懂（"改进这个类" → "改进 MajorMatcher 类：…"）
4. 语言跟原文走（中文原文 → 中文）
5. 不合并两个独立需求；同一需求的多轮追问才合并
6. 附件消息：标准问题点名附件（"分析附件 paste-2.txt（8KB 代码）…"）
7. 短消息：用上下文补全（`fix the err` → "修复 X 的报错"）
8. **不要抄原文**：只给 `msgIds`；输入的 `text` 可能以 `…` 截断，不影响指认来源

### 问题类型枚举（`kinds`）

研究调研 · 技术实现 · 代码调试 · 分析评估 · 方案设计 · 内容写作 · 学习理解 ·
数据处理 · 工具环境 · 其他

`kinds` 为数组：一条消息里的两个独立需求拆成两条问题，各自带自己的 `kinds`。

### 去重与聚类

- **去重**：`orig` 完全相同 → 合并；`std` 高度相似（规范化后相等或 token 重合度高）→ 合并。
  合并即把来源追加进 `sources[]`，永不丢弃。跨对话重复同样合并。
- **聚类**：先从提取结果导出标签词频（`--tags`），据此生成 `qwork/modules.json`
  （10–16 个模块，每个含 `id`/`name`/`desc`/`tags[]`），`--merge` 按该表确定性分配：
  命中标签最多的模块为主模块（并列取表序在前者），其余最多 2 个作副标签。
  兜底模块"未分类"承接未命中的问题。表可人工修订后重跑 `--merge`。
- 标签先做同义词归一（`RAG` / `检索增强` / `检索增强生成` 合并），再聚类。
- 模块命名与 `kinds` 是两个正交维度（模块 = 主题领域，kinds = 提问意图）。

### UI

**`#/questions` 总览**
- 头部：标题、最终条数、口径说明（含去重前后）、搜索框、类型筛选 chips
- 模块卡片网格：模块名、一句说明、问题数
- 附件类可一键筛选/排除

**`#/questions/<module-id>` 列表**
- 问题卡片：标准问题（主体，稍大）· 原始提问（次要色，逐字，可展开）·
  「出现在 N 个对话」（展开列出每处来源与日期）· 副标签 · 复制按钮（标准问题 / 原文）
- 与总览共用搜索与类型筛选

**消息定位**
- 对话页每条消息加 `data-msg="<id>"`；路由扩展为 `#/c/<convId>/m/<msgId>`，
  进入后滚动到该消息并短暂高亮（需在既有的 `scrollToLanding()` 之后执行）

## 本档自行决定（供检查，可不认同）

评审提出的这几项不改变"做成什么"，由本文档定调：

| 议题 | 决定 |
|---|---|
| 一条消息里两个独立需求 | 拆成两条问题；`kinds` 允许为数组 |
| 标签词表 | 允许同义词归一表；先跑一遍再据产出引导词表（模块仍由数据收敛） |
| 提取产物的地位 | `qwork/`（含 `modules.json`）与提取提示词是**保留的输入**，不是可重建的中间产物。这也是它必须放在 `web/data` 之外的原因 |
| 模块的命名 | 模块不由算法机械命名：先从提取结果导出标签词频，跑一次聚类得到 `qwork/modules.json`（{id,name,desc,tags[]} 有序表），`--merge` 再按这张表确定性分配。表本身可人工修订后重跑 `--merge` |
| `--check` 的契约 | schema 校验 + 覆盖校验：每条实质消息至少映射到 1 条问题；每条 `msgIds` 的 id 都能在对话文件里解析到；条数与口径一致 |
| 附件上下文字段 | digest 带附件名与正文前 ~200 字，使 `std` 能自洽 |

## 留给实现者的

- 分片大小（拟 ~30 对话/片 → 24 片）、子代理并发批次与失败重试、可恢复性
- 去重相似度阈值、聚类方法与模块数上限（10–16）
- 模块名与说明的最终措辞
- 问题卡片的具体版式与信息密度
