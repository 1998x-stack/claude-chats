# 标准问题补全任务

你是一个只读的改写器。输入是一批「标准问题」和它们的**完整原始提问**。
上一轮提取时，每条原始消息只给到前 600 字节，**42% 的来源被截断，提取器总共只看到 29% 的原文**，
所以很多标准问题丢掉了细节；有些还保留了只有在那段对话里才成立的指代。

你的工作：把它补成一条**能独立看懂**的标准问题。

## 输入

读：`{{CHUNK_FILE}}`

```
{
  "chunk": 0,
  "questions": [
    {
      "id": "q-0021",
      "std": "现在的标准问题（可能缺失信息）",
      "subject": "现在的一句话主题",
      "kinds": ["技术实现"],
      "tags": ["…"],
      "module": "…",
      "summary": "该对话的英文概述，可能为空",
      "sources": [
        {
          "convName": "对话标题",
          "date": "2026-01-12",
          "orig": "**完整**的原始提问（可能很长）",
          "reply": "Claude 当时的回复开头（≤1200 字节），仅用于判断指代指向什么"
        }
      ]
    }
  ]
}
```

`orig` 是这次的关键：**它是完整原文，不再截断**。请把它读完再动笔。

## 输出

只写：`{{OUT_FILE}}`

```
{"chunk": <与输入相同的 chunk 号>, "questions": [
  {"id": "q-0021", "std": "补全后的标准问题", "subject": "一句话主题", "note": "补了什么/为什么"}
]}
```

- 输入的**每一个 id 必须出现且只出现一次**
- 只输出这三个字段（`id`/`std`/`subject`/`note`），不要加别的字段
- `note` 用一句话说明：补了什么信息，或为什么不需要改
- **紧凑 JSON**：不要缩进、不要美化、不要把字段分行
- 不要 markdown 围栏，不要解释，不要在文件里写别的东西

## 怎么补

1. **先判断这条是否已经自洽。** 如果 `std` 脱离对话就能看懂、且没有丢掉原文里的关键信息，
   **就原样返回**，`note` 写「无需改动」。别为了改而改——411 条里有一部分本来就够好。
2. **解掉悬空指代。** `该`/`这个`/`此`/`上述`/`前述`/`前面那套` 指向的东西，要在 `orig` 或 `reply` 里找到它、
   并在问题里**点名**。例：
   - 「复查上述路线图代码并改进」→「复查 `roadmap.py` 里的路线图生成函数并输出改进后的完整代码」
   - 「结合上面的调研结果构建内容方案」→「结合此前对抖音瓷瓦账号的调研，构建卡地克瓷瓦账号的内容方案」
3. **补上被截掉的那部分里的关键信息**：到底针对哪个项目/文件/工件、要求什么交付物、
   有什么硬约束（格式、语言、长度、技术栈、不要做什么）。这些往往在原文的中后段。
4. **不要写 URL。** 原文里常带 GitHub 链接，改用名字或 `owner/repo`，例如 `1998x-stack/LeetMath`。
   同理，**不要把你写的标识符「加工」出来**：原文说「AI QA system」就写 `AI QA system`，
   不要改写成 `ai_qa_system/deduplication.py`；原文说「Python 代码」不要写成 `main.py`。
   你在 `std` 里出现的**每一个**文件名、路径、函数名、项目名、字段名，都必须能在 `orig` 里找到相同字样。
5. **保留原意与语言。** 这是澄清，不是重新理解：不新增原文没有的要求，不做推测性扩写，
   不把 `reply` 里的答复内容写进问题。中文原文出中文，英文原文出英文。
6. **不要抄原文。** 不要把原文句子直接搬进来；`std` 是你重写的问题。
7. **长度仍然要克制：含中文的问题不超过 120 字；纯英文问题不超过 240 字符。**（含中文就是中文问题，
   即便里面嵌了很多英文标识符，也按 120 算。）信息密度优先，不要写成任务书。原文很长时，
   写清「做什么 + 针对什么 + 关键约束」即可。超长会让整批作废，宁少一个细节也不要超。
8. **`subject` 10–20 字**，是这条问题的一句话主题。

## 反例（不要这样）

- ❌ 只把 `std` 写更长、堆砌原文里的所有细节 → 标准问题变成了任务书
- ❌ 把 `reply` 里 Claude 做的事写成用户的要求 → 那是回答，不是提问
- ❌ 猜一个原文没提的项目名、文件名或路径 → 宁可保留一个较小的指代，也不要编造
- ❌ 改掉 `id` 或漏掉某条 → 每一条都必须原样出现在输出里

如果某个指代在 `orig` 和 `reply` 里都找不到指代对象，**保留它**，并在 `note` 里写明「指代无法确定」。
